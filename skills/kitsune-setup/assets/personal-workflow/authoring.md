# Write personal workflow instructions

Use this guide during setup and every later maintenance change. Its purpose is faithful, scoped instructions, not stronger-sounding commands.

## Preserve meaning

For each proposed requirement, establish when it applies, what the agent should do, what changes that decision, and whether it is a boundary or a usual preference. Include a reason when it helps handle unfamiliar cases.

Do not turn usually into always, this task into every project, or a preference into authorization. Do not invent mandatory documents, a model choice, an agent team, or installation defaults to fill a template. Project requirements remain in their projects.

A current explicit instruction is sufficient evidence. An inferred pattern needs confirmation. Assistant summaries, silence, and incidental details in accepted artifacts are not user approval.

## Language

Write reusable execution procedures in English. Prefer the user's review language for personal preferences, judgment cases, and writing examples. Preserve exact terminology, domain names, commands, and user expressions. Do not translate away distinctions that matter.

If the user wants English personal rules, write one active English version and preserve a short original quotation in evidence when needed. Confirm materially ambiguous translations. Do not maintain conflicting bilingual copies. Set reply language independently of instruction language.

## Make the action observable

Prefer a concrete action and condition over labels such as professional or autonomous. For a broad request like "stop asking about everything," propose a scoped interpretation rather than granting unlimited authority. For concise writing, identify what to omit; do not invent a word limit that hides important findings.

Keep active instructions short. Provenance, drafts, and unresolved alternatives belong in maintenance notes, not startup content. Merge equivalent requirements instead of accumulating duplicate prohibitions.

For revisions, use maintenance's [change selection](maintenance.md#choose-the-smallest-change) and [before-and-after checks](maintenance.md#plan-before-and-after-checks). Edit the affected content rather than regenerating the whole profile. A merge must preserve distinct conditions, exceptions, terminology, and obligations; shorter text is not sufficient evidence of improvement. Retire superseded guidance instead of leaving two active versions. When moving detail out of the core, retain its applicability and reading path; do not hide an authorization boundary because it is rarely used.

## Scope, exceptions, and local precedence

Multiple applicable requirements do not necessarily conflict. Check whether they can be satisfied together or apply to different situations before assigning precedence.

Prefer one clear default with a conditional exception when the requirements describe the same preference. If separate requirements genuinely conflict, add a confirmed local relationship using their stable identifiers or links. State when both apply, which action takes precedence, which part yields, and which obligations remain. Put this near the relevant requirement, not in a global numeric ranking.

Only override the conflicting part. For example, a confirmed learning-mode exception may allow necessary explanation despite a brevity preference; it does not remove evidence limits, reply language, or other compatible requirements. Include a near-miss where the exception must not activate.

Do not derive precedence from stronger wording, file position, reading order, or specificity alone. Do not assume that A overriding B and B overriding C establishes A over C without checking their conditions and the confirmed meaning. A cycle is a possible conflict to inspect, not proof that mutually exclusive conditions are inconsistent.

Use current task-specific instructions within their authority without turning them into permanent profile changes. Personal relationships never grant permission to bypass host restrictions or task authorization. A new skill is not a new source of user authority.

Keep unconfirmed relationships out of active content. For a material unresolved conflict, ask about the concrete choice and continue independent work. Routine, reversible choices within authorization may use established defaults without inventing a permanent priority rule.

## Use examples selectively

Simple requirements may need none. Style and judgment boundaries may benefit from a short example that changes one relevant condition. Label the situation, expected action, and reason. Show the correct alternative next to any prohibited behavior.

Keep examples consistent with the rule. Avoid accidental patterns such as a fixed project name or filename. Store long examples with the relevant method and state when to read them. Keep some evaluation cases out of normal prompt material.

More examples are not automatically better. After a failure, first check whether the rule is unclear or an example contradicts it. Do not treat extra context as a substitute for a missing capability or permission control.

## Review before activation

- Is the scope supported by the user's words or confirmed interpretation?
- Does it conflict with existing active guidance or a selected skill?
- Can related requirements coexist, or is a confirmed conditional exception needed?
- Do relationship references resolve, and does the override preserve non-conflicting obligations?
- Have materially ambiguous conditions, possible cycles, and outdated examples been resolved or left explicitly unconfirmed?
- Does it add an unauthorized action or an unnecessary procedure?
- Does the example teach the intended condition rather than incidental details?
- Can a suitable case and a near-miss case distinguish correct behavior?
- Are the user's terminology and desired reply language preserved?
- Does the chosen operation fix the diagnosed cause without unnecessary new guidance?
- Which previous obligations must still pass, and what behavior remains unverified?

Do not claim compliance from wording alone. File checks and actual behavior checks are separate.
