# 使用指南

## 安装入口

把这句话交给能读取本仓库的 agent：

```text
请读取这个仓库的 INSTALL.md，为当前 agent 安装 kitsune-mode 和 kitsune-setup。
```

会话不在仓库时，给出 `INSTALL.md` 的实际路径。[安装流程](../INSTALL.md)会识别当前宿主，寻找受支持的位置，再安装两个完整目录及支持文件。仅存在于本仓库不代表宿主已发现它们。不要求先安装第三个 skill，也不假设所有工具扫描同一路径。

用户未指定位置时，使用实际宿主的个人技能目录。用户指定集中安装目录时，核对发现机制并在支持时建立链接；不把维护者使用的目录作为所有用户默认。默认只安装当前宿主，需要多个工具时明确列出。

安装只写获准的技能目录和发现链接，不生成个人工作流、不启动访谈、不写 `CLAUDE.md`、`AGENTS.md`、hooks 或权限设置。更新已有副本前先比较内容，保留本地绑定和用户改动；旧版全局入口需要单独审阅迁移，不能直接叠加。Node 是维护工具与 Claude command-hook 适配器的运行条件，安装包并不授权安装 Node 或启用自动维护。

`kitsune-setup` 只在用户要求配置时使用。它包含 Claude 风格的手动调用标记和 Codex 的隐式调用限制。其他工具可能不识别这些字段，正文仍明确限制用途。不要声称这些字段提供跨工具权限控制。

## 各阶段写什么

| 阶段 | 可能写入的内容 | 不会顺带做的事 |
|---|---|---|
| 按 `INSTALL.md` 安装 | 两个技能的完整副本、当前宿主需要的发现链接 | 不生成偏好，不改个人启动文件或启用 hooks |
| 主动调用 `kitsune-setup` | 经审阅的个人目录、`maintenance.json`、获准的可选本地绑定 | 不替日常入口进行宿主接入 |
| 首次使用 `kitsune-mode` 接入 | 获准宿主的个人启动文件、接入记录，以及单独获准的维护 hooks | 不自动给所有工具改配置，不改无关设置或权限 |
| 已启用的日常维护 | 既有目标内的个人指导、`.maintenance/` 私有记录、授权内的恢复与清理 | 不自行改维护执行策略、配置、预算、hooks、权限或业务项目文件 |

个人启动文件可能是 `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`，也可能因宿主配置而不同。先核对实际加载机制和授权再写入；没有可用机制时保留 skill 激活方式。具体读取来源见[接入说明](integration.md#宿主还会读取什么)。

## 配置个人目录

显式使用配置入口，简短说明希望覆盖的工作范围。可以提供零个、一个或多个项目、交付物、片段或任务描述，每个来源分别确定用途、允许读取的范围和排除项。过程中可以追加来源，agent 应只复核受影响的结论，不重启整个访谈，也不把一个来源的授权扩展到其他来源。

agent 先有限预读，再用通用框架检查目标与产物、执行方法、质量标准、验证证据、取舍与例外、协作方式。框架用于发现缺口，不预置用户偏好。开发、调研等宽泛标签只是导航，重要场景要细化到有输入、产物和约束的具体任务。

关键任务不仅讨论何时做什么，还要有可审阅的方法草稿和质量判断依据。agent 可提出步骤和可信对照，由用户纠正关键判断，不要求用户设计每个实现细节。没有明确方法或质量要求时，保持开放或暂缓状态，不把问过决策问题当成完全覆盖。简单事项、已委托判断和有理由的不适用项不需要硬凑问题。

宿主支持选择界面时，有限选项使用该界面，同时允许其他回答和暂缓。结束前明确补查遗漏任务、可追加资料，以及是否还有知道要做什么却不知道怎样做好的任务。详细步骤见[访谈说明](../skills/kitsune-setup/references/interview.md)和[覆盖框架](../skills/kitsune-setup/references/framework.md)。

审阅生成的行为摘要、选定技能和文件范围。个人目录按固定顺序确定：本次明确指定的路径优先，其次沿用已有绑定，两者都没有时使用 `~/.kitsune/workflow/`。`~` 表示实际宿主用户的主目录，不是当前项目目录。

不需要每次重新选择保存位置。创建前展示解析后的实际路径，已有文件先检查再修改，不静默覆盖。绑定无效或已选目录不可用时报告问题，不悄悄退回默认位置生成另一份配置。个人内容使用你能准确审阅的语言，回复语言单独设置。

已有个人目录时说明这是更新，避免生成平行副本。后续变更统一读取其中的 `maintenance.md` 和 `authoring.md`，保留已有有效方法。若要从旧的逐次确认流程迁移到自主维护，需要在本次迁移中明确包括执行策略、配置和授权边界的变化，不能只复制新安装包就宣布已启用。

首次配置一并审阅日常维护范围：`maintenance.json` 启用迭代，记录写入个人目录下的 `.maintenance/`，每次复核最多一组自动修复，并保留检查与针对性恢复依据。默认 `maxIssues` 为 100，`minIdleDays` 为 30；设为 `null` 可停用时间门槛。这里只建立个人维护授权，宿主启动文件和 hooks 仍在接入阶段单独确认。

## 绑定日常入口

配置入口可在获准后，给已安装的日常 skill 写入 `local/workflow.json`，记录版本 `1` 和绝对 `workflowRoot`。这个文件是本机数据，不应提交到可复用源码。

宿主不允许写本地绑定时，默认目录仍可按约定定位。如果使用自定义目录且没有可保存的绑定，需要在激活时提供该路径。默认目录尚不存在时，日常入口会提示配置，不会在普通任务中自行创建。

## 日常使用

完成绑定后，直接提需求。模型可以选择日常入口，也可手动激活。它读取个人核心，按需补读方法和选定技能，不会重新运行配置访谈。

首次激活时，日常入口会检查启动加载能力，说明具体修改并请求尚缺的授权。Claude 自动维护使用单独的 command-hook 适配器，在当前会话里给 agent 一个简短内部复核入口，不启动另一模型、后台 agent 或守护进程。实际接入方式见[接入说明](integration.md)。已接入后不应每轮重写设置；已经拒绝也不应反复提示。

个人核心仍只有 `README.md`、`preferences.md` 和 `skills.md`。维护指南按需读，不在启动时灌入 `.maintenance/` 或配置证据，也不默认扫描所有旧会话。

## 自主维护怎样工作

完成初始授权并启用后，agent 在日常工作中根据实际产物、错误、纠正和检查结果复核问题。先看任务是否真正失败，再查加载、方法发现、执行、表达或能力原因；已有规则够用时修正执行，不再追加同义禁令。没有问题或没有充分依据时，可以结束复核而不改文件。

范围内维护不要求你每次说“记住”、审阅提案或阅读维护报告。当前任务的纠正本身不是新的通用偏好；agent 可以在既有目标下推导修复方法，但不能凭空决定你的价值取舍。明确要求不持久化时照做。真实任务的新目标、尚未对齐的重要选择和权限仍需询问并等待。

问题、发生记录、原因假设、尝试与检查结果存为多对多关联，一个修复可以服务多个问题。每次复核最多一组有证据依据的自动修复；没有新证据就停止重复失败策略。复发时重新诊断，不机械回滚最近改动。应用和恢复前检查版本与依赖，保留同文件中独立的后续编辑，也不恢复你已废止的偏好。

自动修复可以调整个人偏好、方法、例子、索引和编写指南，不能自行改 `maintenance.md`、`maintenance.json`、预算、hooks、权限或安装。私有记录按数量和最后有意义的更新时间有界清理，只有超出上限才从旧到新删除符合年龄门槛的记录；不足时允许暂时超额。不要求问题已经解决，删除记录也不撤销已经生效的工作流修改，不另建无限冷库。

“安静”指不把维护过程变成日常对话负担，不是隐藏宿主工具轨迹、安全提示或真实任务的限制。文件检查、实际 hook 事件和模型行为仍分别记录，不能以模型自评宣称维护有效。工具用法见[维护运行指南](../skills/kitsune-mode/references/maintenance.md)。

## 更新和停用

你可以只纠正当前答案，也可以明确改变长期偏好。清楚的持久修改请求不需要再次批准同一范围；未经委托的新个人价值或未决冲突才需要确认，不把普通修复方法的推导也变成反复访谈。

启动加载、个人维护开关和宿主 hooks 是不同层。要求停用时明确停用哪一层，只改获准的配置或受管理内容并记录状态；停用 hooks 不会自动删掉启动核心，停用启动导入也不等于删除 hooks。个人文件和已安装技能仍然保留。完全卸载或删除个人资料是另外的操作，不作为停用副作用。
