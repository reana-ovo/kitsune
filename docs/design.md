# 当前设计

2026-11-07，用户确认以个人工作方式为目标重建 kitsune。该文档记录本轮采用的方案，后续直接修改，不使用 RFC/ADR 审批流程。

## 产品边界

Kitsune 提供两个技能入口、个人目录模板和维护方法，复用宿主 agent 的文件工具、上下文、权限和可选代理能力。不自建 agent 运行程序，不默认组建专家团队。

个人工作流描述用户怎样表达、取舍和检查工作。业务项目的规范仍由项目管理，不提取成跨项目偏好。用户资料和机器路径留在本地，不成为可复用技能的默认内容。

## 配置流程

1. 简短确认希望覆盖的工作范围，接受零个、一个或多个项目、交付物、片段或任务描述。逐来源确定用途、读取范围与排除项，目录外会话单独授权。
2. 先跨获准来源有限预读，再用独立框架检查目标与产物、执行方法、质量标准、验证证据、取舍与例外、协作方式。项目提供证据，不决定整个访谈范围。
3. 将重要场景细化为有输入、产物和约束的具体任务，按问题依赖深入。agent 查证事实、提出方法草稿和可信对照，用户决定尚未委托的关键判断，不逐项确认普通实现细节。
4. 跟踪各维度的已明确、已委托、不适用、暂缓和未决状态。重要的方法或质量缺口仍存在时，不因为决策问题问完就标记完全覆盖。
5. 允许中途追加来源，只复核受影响的证据和结论。比较各项目的目标与环境，不按第一个项目或出现频率决定个人规则。结束时补查遗漏任务、资料和方法深度。
6. 区分明确要求、待确认推断、单次限制和项目规则。根据需求推荐少量技能，也允许不选择任何技能。
7. 展示行为、重要方法、质量判据、例子和文件操作范围，确认后保存个人目录。已有明确授权不重复确认；推荐或候选方法不等于用户决定。
8. 检查产物及绑定状态。真实模型评测与安装、启动接入需对应授权。

[访谈框架](../skills/kitsune-setup/references/framework.md)规定要了解的维度，不规定所有用户必须采用相同工作流程。场景和维度都不是一对一的 playbook、文件或 skill 列表。简单事项按需要缩短，专业问题随实际任务补充。宿主提供选择界面时，有限选项使用该界面并保留自定义回答和暂缓；开放讨论或不支持界面时使用文字。

## 个人目录

必需内容是入口 `README.md`、`preferences.md`、`skills.md`、`maintenance.md` 和 `authoring.md`。没有选中技能时清单明确写无，不伪造技能能力。

按需增加方法、例子和证据。未确认推断只放在证据或草稿，不作为启动指令。首次生成和后续维护共用随个人目录保存的编写指南，不依赖安装源码永远存在。

短核心与方法索引可以启动加载，详细方法按任务读取。重要方法应保留输入和结果、执行步骤中的判断与调整、独立的质量判据，以及如何验证和何时停止。确认过的方法与质量信息不能在生成时退化成只有触发条件的偏好条款。多个任务可以共用方法，简单要求不强制生成方法文件。

少量例子解释有歧义的判断，也可用可信成果对照说明两种可行做法的质量差异，不给每条要求机械添加例子。留一部分新案例做检查，不能只测试提示里已有的答案。访谈框架、来源清单和未决覆盖项不进入日常核心。

## 语言

入口 skill、共用步骤、维护说明和代码注释用英语。个人偏好、场景和表达示例优先使用用户能准确审阅的语言。保留具体术语、原话与命令。用户选择英语个人规则时，仍检查翻译是否改变范围或语气。

回复语言单独记录。英文指令不意味着默认英文回复。同一要求只有一份生效版本，不同步维护可能分歧的中英文全文。

## 日常加载与首次接入

个人目录按固定顺序定位：本次明确指定的路径、安装目录旁的已有绑定、默认 `~/.kitsune/workflow/`。配置入口和日常入口使用同一顺序。`~` 按实际宿主用户的主目录解析，不包含固定用户名。

绑定无效或已选路径不可用时报告问题，不静默换目录。默认位置尚不存在时，只有在获准的配置流程中才创建，不在日常任务中扫描主目录或生成另一份配置。

首次激活时检查宿主。支持原生导入就优先导入；只有自动加载指令文件的能力时，可以生成受管理的核心内容；都不支持或用户拒绝时，保留 skill 激活方式。不同工具的接入不同，个人内容共用。

自动加载保证的是文件内容进入上下文，不是模型必然遵守。只写“请读取另一文件”仍然依赖模型主动读取。已经接入或已拒绝的宿主不在每次任务重复改写或询问。

个人核心保留修改判断和维护入口，因为完成接入后可能不再调用日常 skill。新增工具和同步到新位置不等于已获授权。

## 规则的范围与局部关系

访谈只检查同一场景、动作或输出维度上有关联的要求，以及历史中出现过的取舍，不让用户给全部规则排名。能同时满足的要求共同生效；适用范围不同的要求先分清条件。

生成时优先把默认和条件例外写在一起。必须分开表达时，用稳定标识或链接记录已确认的局部关系，说明触发条件、让步部分和仍然有效的要求。不按编号、文件顺序、措辞强度、读取先后或更具体的文字自动决定效力。

个人核心包含冲突处理顺序，因此原生启动加载和受管理的内嵌内容都会带上它。已知关系按条件处理；重要未决冲突只询问具体选择，其他独立工作继续。常规、可逆且已授权的判断使用既有默认，不自动生成永久优先关系。

个人规则关系不能扩大权限。本次任务的临时选择不会自动改变长期偏好。维护时检查关系引用、例子、选定技能及潜在循环，不跨不同条件盲目推导传递关系。

相关依据见[优先关系研究](research/2026-11-07-rule-precedence.md)。当前实现是说明与模板，没有规则引擎，也尚未运行对应的模型行为测试。

## 统一维护

任何持久修改先读取个人 `maintenance.md`。只修当前任务不自动保存；明确长期要求按已给授权更新；推断、冲突或扩大范围先确认。规则已经存在但未遵守时，先修正执行，不添加重复规则。

更改唯一内容来源，调整相关例子和检查。受管理的启动副本需同步，无法同步时明确报告。维护规则不能由 agent 自行放宽。此流程是参与者约定，不是文件系统权限控制。

维护先诊断加载、方法发现、执行、表达、冲突、偏好变化或能力缺口，再选择不修改、澄清、合并、替换或停用、移到按需内容、确有缺失时新增。局部修改优先，不通过反复重写整份文件或单纯压缩字数来优化。低频授权边界不能因使用次数少而删除，历史与草稿不进入启动核心。

修改前确定预期改善和应保留的行为，选取原问题、可能受影响的正确案例、例外边界及未写进运行示例的新案例。实际模型对照需要授权，条件应可比；检查具体失败，不以平均分掩盖边界退步。未运行行为检查时，允许按明确授权修改，但如实报告未验证。失败优化应修改、拒绝或在授权内局部回滚，不恢复已被用户废止的偏好，也不覆盖无关的后续编辑。

这些步骤保存在按需读取的维护与编写指南中，不扩大每次启动的个人核心，不增加自动反思、逐任务改写或自动淘汰规则的机制。

## 第一版验证边界

静态检查覆盖源码、模板、样例和启动预览工具。没有运行新的 agent 会话、自动触发实验或跨工具行为评测。可选预览工具只输出拟议内容，不写用户配置。

可复用源码不代表本机已安装；本机安装或清理需要对应授权并单独核对。活跃源码已重建，旧实现及讨论原文保存在维护者本地的 `archive/`，不纳入 Git，不作为新检出的必需文件。
