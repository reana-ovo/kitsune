# Kitsune

[English](README.md) | [简体中文](README-cn.md)

**为 AI agent 建立一套属于你的工作方式。**

你可能反复告诉 agent：选技术前先查维护情况，比较方案时先给推荐，修改实现时一起更新文档。有些要求适用于所有工作，有些只在特定任务中成立。把它们不断追加到一份全局提示里，很容易留下重复、冲突和过时的内容。

Kitsune 通过访谈把这些要求整理成你能审阅和维护的个人文件，再让 agent 在日常任务中按需使用。你决定工作方式，项目继续管理自己的开发规范，宿主继续管理工具和权限。

## 它如何工作

Kitsune 由两个 skill 组成：

| Skill | 用途 |
|---|---|
| `kitsune-setup` | 了解你的工作、讨论要求与取舍，生成或更新个人工作流。由你主动调用。 |
| `kitsune-mode` | 日常读取个人工作流，选择相关方法和技能，并处理获准的启动接入与后续维护。 |

它们复用当前 agent，不额外运行模型或独立服务，也不要求特定模型或多 agent 团队。指导内容仍是可直接阅读、编辑的 Markdown 文件；一个小型 Node 工具负责私有维护记录、版本校验、改动恢复和清理。单独启用的 Claude command-hook 适配器会在当前会话内触发复核。

例如，你可以表达这样的要求：

> 比较技术方案时先给推荐，并说明维护和兼容性依据。普通进度汇报保持简短，但我要求学习原理时，要保留理解所需的步骤。

配置过程会进一步确认这些要求的适用范围、例外和可观察的行为，而不是把每句话都变成一条无条件命令。上面只是示例，不是预置给所有用户的偏好。

## 快速开始

### 1. 安装两个入口

获取仓库的本地副本，把下面这句话发给你的 agent：

```text
请读取这个仓库的 INSTALL.md，为当前 agent 安装 kitsune-mode 和 kitsune-setup。
```

如果会话不在仓库内，给出 `INSTALL.md` 的实际路径。agent 会根据[安装说明](INSTALL.md)确认当前工具的技能位置，检查已有内容，再安装两个完整入口。

默认使用当前宿主支持的个人技能目录。需要集中管理时，可以在请求中指定其他位置，例如 `~/.cc-switch/skills/`。安装不会直接生成个人偏好、开始访谈或改写全局启动指令。

### 2. 配置你的工作方式

在支持斜杠技能命令的 Claude Code 中输入：

```text
/kitsune-setup
```

其他工具使用其手动调用技能的方式。

先说明希望覆盖的工作范围，并提供零个、一个或多个参考项目、交付物或片段，以及各自的读取边界。过程中可以继续追加资料；没有可分享资料时，也能通过任务描述开始。

agent 预读后，会按目标与产物、执行方法、质量标准、验证证据、取舍与例外、协作方式检查覆盖，不把参考项目当成全部工作。重要场景会细化成具体任务，通过方法草稿和成果对照讨论“怎样做才算做好”，再检查遗漏，给你审阅拟生成的内容和可选技能。已委托的普通判断不需要逐项确认。

确认后，个人文件默认保存在 `~/.kitsune/workflow/`。你明确指定的路径或已有绑定优先。首次审阅一并说明维护范围、`maintenance.json`、私有记录和保留策略。参考项目的规范不会自动变成你的跨项目个人要求。

### 3. 在日常任务中使用

让 agent 使用 `kitsune-mode` 处理后续请求。支持自动选择技能的工具可以自行选择它，也可以由你手动调用；仅安装文件不能保证每次请求都触发。

首次使用时，日常入口会检查宿主是否支持启动加载，并在获得对应授权后接入。支持原生导入时使用导入，否则可以采用受管理的核心副本；没有可用机制时继续使用 skill 激活方式。启用 Claude 维护 hooks 是单独的宿主接入选择，不是安装副作用；其他宿主可使用通用维护流程，但不因此宣称已支持自动事件。

具体步骤见[使用指南](docs/usage.md)。如果你想观察完整的首次使用过程，见[从零配置实验](docs/first-run.md)。

## 你的工作流包含什么

```text
~/.kitsune/workflow/
├── README.md          # 入口、加载方式和维护判断
├── preferences.md     # 已确认的个人要求与适用范围
├── skills.md          # 选用的技能、用途和可用状态
├── maintenance.md     # 诊断、修复、检查和恢复的执行策略
├── maintenance.json   # 迭代开关与记录保留配置
├── authoring.md       # 如何准确表达个人要求
├── methods/           # 按需的具体工作方法
├── examples.md        # 按需的判断与表达示例
├── evidence.md        # 按需的配置来源和待确认事项
└── .maintenance/      # 按需建立的私有问题与关联记录
```

`methods/`、`examples.md` 和 `evidence.md` 只在需要时生成，不为填满模板而虚构内容。启动核心仍是 `README.md`、`preferences.md` 和 `skills.md`，不整批加载历史、运行记录、配置或详细维护指南。

想先看看结果，可以阅读[虚构用户样例](examples/personal-workflow/README.md)。它用于展示结构，不应直接当成你的配置。

## 随使用改进，而不是不断追加规则

首次配置与宿主启用建立范围后，正常维护自主、安静地进行。agent 可以依据任务失败、纠正和检查结果，在既有目标内改进方法，不需要你每次说“记住”，也不逐次提案和汇报。当前任务的反馈不会变成通用偏好；新目标、尚未委托的个人取舍和额外权限仍需你决定。

维护先看实际结果，再查原因。文件未加载、方法未发现、已有要求未执行，并不都需要新增规则。每次复核最多进行一组有证据依据的修复，检查效果，并通过版本校验和针对性恢复保留独立的后续编辑。复发要重新诊断，不能机械回滚最近一次修改，也不能没有新证据还重复失败策略。

问题、发生记录、原因、尝试和检查之间用关联表达，不强制一一对应。默认保留上限是 100 个问题，闲置门槛为 30 天；`minIdleDays` 设为 `null` 可取消时间条件。只有超出数量上限才按最后有意义的更新时间从旧到新清理，符合条件的记录不足时允许暂时超额。不要求问题已经解决，也不转移到无限增长的冷库。

没有固定规则数量目标，不默认扫描旧会话。自动修复不能改自己的执行策略、运行配置、预算、hooks 或权限。安静维护不隐藏宿主审计轨迹和安全提示；本地工具正常运行，也不证明模型归因或行为已经改善。详见[设计说明](docs/design.md)和[维护工具指南](skills/kitsune-mode/references/maintenance.md)。

## 兼容性与边界

- 宿主需要能使用 skill，并读取相关文件。不同产品的安装位置、调用方式和启动加载能力不同。
- 安装说明列出了 Claude Code 和 Codex 的常见本地技能目录。其他工具，包括 Cowork，需要先确认实际安装与持久存储机制，不能直接套用本地目录。
- 启动加载只意味着内容进入上下文，不保证模型遵守。个人文件也不能替代宿主权限控制。
- 入口和共享执行步骤使用英语。个人要求与例子使用你便于审阅的语言，回复语言单独约定。
- Kitsune 不捆绑可选第三方技能。选择某项能力不等于授权安装、升级或执行它。

更多说明见[接入与兼容范围](docs/integration.md)。

## 参与开发

修改前阅读 [AGENTS.md](AGENTS.md) 和[设计说明](docs/design.md)。技能指导仍是文件指令；Node.js 用于本地检查、可选的启动修改预览，以及维护工具和 Claude 适配器。

运行检查：

```bash
node tests/check-workflow.mjs
```

检查覆盖文档链接、技能结构、模板与样例一致性，以及本地文件处理契约。Runtime fixture、合成 hook payload、真实宿主事件和模型行为是不同证据。命令和验证范围见[检查说明](docs/testing.md)，不能用这些检查替代实际行为证据。

反馈实际使用问题时，请说明使用的宿主、操作步骤、预期行为和实际结果。不要附带凭据或未经处理的私人对话。
