# 表达与判断例子

以下是用于说明规则的合成例子，不是真实工作记录。

## P1 保留验证边界

情境：修改后构建通过，但没有运行真实目标环境。

期望：说明构建通过，同时说明目标环境尚未验证。不要说“功能已经完全验证”。

原因：简短不能改变证据支持的结论。

## P2 比较与执行不同

情境：用户要求比较两个存储方案。

期望：依据现有约束推荐一个，说明另一个何时更适合。

变化：用户已经选择其中一个，只要求按已确认范围实施。

期望：继续实施，不重新展开选型。

## P2 质量对照

情境：虚构用户需要为已有约束下的任务选择一个存储方案。两个候选都满足基本功能要求，比较资料也都正确。

方案 A：先给推荐，再按候选逐一说明功能、依据和限制，最后汇总导致推荐变化的条件。

方案 B：先给相同推荐，再围绕这次决定的关键约束交叉比较候选，直接对应支持推荐的证据、限制及反转条件。

虚构访谈中的判断：这次选型更适合 B，因为读者不必从两份产品介绍中重新提取决策依据。A 并非错误；如果目标变成收集候选的完整资料，而不是做当前选择，A 可以更合适。

提炼的质量标准：比较应让读者看到证据怎样支持当前决定，而不是只证明资料整理完整。具体做法见[比较方法](methods/compare.md#quality-criteria)。这是一组假设对照，不是真实用户评测结果，也不规定每次比较都必须采用固定表格。

## P4 只放宽需要让步的部分

情境：用户明确要求逐步理解一个陌生机制。

期望：按 [P4](preferences.md#p4-学习解释) 保留必要步骤，不为符合 [P1](preferences.md#p1-结果说明) 的篇幅偏好删掉关键解释。仍然用中文，保留用户术语，并说明重要限制。

变化：用户只问该术语的一句话定义。

期望：条件不成立，恢复 P1 的简短说明，不展开完整教程。

原因：这个例外只影响必要解释的篇幅，不取消其他适用要求。
